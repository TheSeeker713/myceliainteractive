# Development log — September 6, 2026

**17:32 UTC — I tightened the production rules and finished an audited repair plan without touching the website itself.**

I wanted the next round of work to slow down at the right places. The old rules already required approval, tests, and an automatic push, but they did not draw a hard enough line between a phase and the steps inside it. I changed that. Every implementation step now needs its own approval. At the end of a phase, the work stops on production until I test it myself and return a report with the next greenlight.

The testing rule is stricter now too. Every required command and any focused checks have to pass twice, completely. A partial result is a failure. Once both passes are clear, the day's work goes into this one dated log before anything is committed or pushed. This should leave a readable record instead of scattering the day across a pile of tiny files.

I also reviewed the plan for the broken liquid background on MacBook Chrome and the trackpad problem that can skip multiple cards. The current code gave us two useful leads. The onboarding button dismisses the dialog, but it does not directly tell the moving background to retry playback during that click. The card transition code can also hold another direction while an animation is running, which means the momentum from one trackpad swipe may be treated like a second swipe. These are leads, not conclusions. The first phase is written to collect evidence on the actual MacBook before changing the background. The trackpad work comes afterward so it does not muddy the first diagnosis.

The repository passed the production build, lint, TypeScript check, and all 148 tests twice after the plan audit. I did not change any component, animation, scrolling behavior, test, or deployment configuration during this step.

**19:18 UTC — I pulled the repair plan apart and rebuilt it around evidence instead of letting a good guess turn into production code.**

The first version had the right order, but it packed too much into the first diagnostic step. It could have gone from looking at the Mac problem to writing and deploying diagnostic code without a clean stop in between. I split that work up. The plan now starts with the actual production baseline and a no-code comparison between the MacBook and Windows laptop. Diagnostic code is conditional. If the browser evidence is enough, that step gets skipped.

The eight-second fallback needed to be called out directly. Right now, if the video texture does not become ready in time, the atmosphere falls back to the poster and removes the video and canvas from the rendered output. That means the onboarding click may arrive after the thing it is supposed to wake up is already gone. The revised plan tests both sides of that timeout and requires the click to make its recovery attempt during the click itself. It also records playback, decoded-frame, texture, WebGL, and user-activation state separately so we do not lump every static-background failure under autoplay.

I tightened the trackpad section too. Raw wheel values are not enough to tell us where one physical gesture ends. The next version has to account for momentum, pixel versus line deltas, diagonal motion, pinch-zoom, and whether the gesture began inside the card. One swipe gets one card. Reaching the end of text inside a card does not quietly turn the same swipe into page navigation. Keyboard, mouse-wheel, hash navigation, mobile drag, browser zoom, and the background input still have to survive the change.

This was documentation work only. No component, animation, scrolling logic, test, asset, or Cloudflare configuration changed. The production build, lint, TypeScript check, and all 148 tests passed twice after the plan was rewritten. The website problems are still open, and no repair step is approved just because the plan is more complete now.

**Jeremy Robards, CTO and CAIO, Mycelia Interactive**

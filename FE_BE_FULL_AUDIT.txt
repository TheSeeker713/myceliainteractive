7. FIRESTORE & SESSION FLOW
================================================================================

Session Lifecycle:
  1. WS connection opened → getOrCreateSession() called
  2. Session created in Firestore (or memory fallback)
  3. Game state tracked: currentStep, trustLevels, cardsCollected,
     dreadTimerActive, sceneHistory
  4. updateSession() called on every state change
  5. WS close → all timers cleared, Gemini sessions closed

Data Model (state.ts):
  - PlayerState: trust (float 0.0-1.0), inventory, flags
  - GameSession: sessionId, playerState, chatHistory, metadata
  - ChatMessage: role, content, timestamp

Failure Handling:
  - Firestore unavailable: Falls back to in-memory store
  - No explicit Firestore timeouts (low-impact for demo)
  - Session cleanup on disconnect is thorough

VERDICT: Correct. Firestore CRUD working. Fallback present.

11. RUNTIME ERROR RISK ASSESSMENT
================================================================================

Scenario                          | Handling                    | Risk
----------------------------------|-----------------------------|------
Firestore unavailable             | Memory store fallback       | LOW
Gemini API timeout                | try/catch + ws.close()      | LOW
Imagen generation RAI block       | Returns null, uses fallback | LOW
Veo generation RAI block          | Returns null, still image   | LOW
WS close during async operation   | readyState check before send| MEDIUM*
Player frame not received         | Reuses previous (stale)     | OK
Step 31 reached                   | Gate prevents progression   | OK
Card pickup timer expires         | onExpire → game_over        | OK
Dread timer expires               | game_over broadcast         | OK
JSON.parse() on WS message        | try/catch + binary fallback | GOOD
Frontend WS disconnect            | 3-retry reconnect backoff   | GOOD

* MEDIUM: Minor race conditions possible if WS closes mid-async chain.
  Negligible for demo — would cause a missed event, not a crash.
